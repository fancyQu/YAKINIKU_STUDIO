# Android 实时识别与保存：需求及适配评估

评估日期：2026-11-02。依据现有源码和 Android 平台能力整理，未进行 Android 真机验证。本文用于明确开发范围，不代表当前项目已经支持安卓。

## 已确认范围

用户要求：**手机版只做实时识别以及保存；手机本地识别，脱离电脑使用。**

结合现有日语直播业务，本文按「采集直播音频 → 实时日语转写 → 保存音频、日语文本及时间轴」评估。保存范围暂按同时保存音频和文本理解。

不纳入手机版首版：中文翻译、Qwen、本地大语言模型、MiniMax 文件精修、独立校对、Space 浏览器扩展。桌面端原有业务不因此改变。

执行位置已确认：手机本机。首次明确下载模型后，采音、识别、保存、回放和导出均可离线完成，不依赖电脑、云端语音接口或 API 密钥。

建议架构：Android 原生采音 → 手机分段保存音频 → VAD／短片段调度 → whisper.cpp 本机识别 → 日语文本与时间轴持久化 → 回放和导出。识别进程不能阻塞采音与保存。

## 最小业务流程

1. 用户开始录制，授予必要权限，在系统界面确认音频采集。
2. 原生采音模块持续接收直播声音，先将音频分块保存到手机，再提交短片段识别。
3. 页面逐段显示日语转写；每段记录实际音频的起止时间、识别状态及模型身份。
4. 识别跟不上时继续保存音频，显示积压；识别队列只保存文件范围等小型引用，不无限堆积 PCM。
5. 停止时先完成音频尾部保存，明确区分「音频已保存」和「文字仍在补全」。允许停止后补全未识别片段。
6. 历史记录支持回放、查看识别文本、导出音频、日文 TXT 和日文 SRT。导出音频不依赖识别成功。

实时识别按短音频分段持续运行。Whisper 方案需要处理分段边界、重叠文字去重和最终确认，不能把模型名称等同于逐字流式识别，也不预先承诺固定延迟。

## 差异化定位与建议增量

用户进一步要求做出差异化。推荐定位为：**帮助日语直播观众和字幕整理者，在手机离线记录直播、回找原话、整理精彩片段的工具。**

只提供日语转写时，优先服务有一定日语基础、需要核对原话或整理素材的人。若面向完全不懂日语、希望当场理解内容的人，仍需要翻译能力；本节沿用已确认的「手机仅识别及保存」范围。

离线、本机模型、保存和字幕导出不足以单独建立明显差异。推荐把以下功能做成连续的操作体验；这是产品方向建议，未进行竞品逐项实测，不宣称这些功能独有。

| 能力 | 用户获得的具体价值 | 实现及验收边界 |
| --- | --- | --- |
| 点击转写，回听对应原音 | 识别有误或没有听清时，立即核对上下文 | 以片段时间轴定位，可从该段前数秒播放；首版不承诺逐字对齐。直播采音期间默认通过书签暂存回听位置，回听播放应避免重新混入录音 |
| 观看时标记精彩片段 | 不用记时间，也不用等待识别完成 | 可从前台服务通知操作「标记刚才」，以采样时钟记录位置；从书签调整前后范围，录制后导出音频及对应日文字幕。源 App 不允许内录时，此功能不能解决采音限制 |
| 完整录音与可见的待识别范围 | 手机发热或模型跟不上时，仍能保住素材 | 采音、落盘与识别分离；保存失败应明确停止，识别失败不删除录音。书签不依赖 ASR 是否完成 |

例子：直播中听到想整理的一段对话，在通知栏点击「标记刚才」。结束后从书签进入，回听前后文、调整片段范围，再导出这段音频和已完成的日语字幕。若对应文字仍待识别，先提示补全或单独导出音频。

建议首版围绕「实时转写、可靠保存、按段回听、直播书签」交付。书签先保存时间点与范围引用，避免录制时反复复制大段音频；片段导出在停止录制后执行。待识别、用户标记待核对和已确认文本分开显示，不把模型内部概率展示为经过验证的准确率。

第二阶段再评估两项能力：

- **主播／节目词表**：用户保存人名、昵称、常见术语和读音，作为识别提示；原始转写和人工修改分开保留。词表是否改善识别需用真实样本验证，不承诺填写即准确。
- **桌面继续精修**：通过用户主动导出的项目包，携带原音、转写、时间轴和书签，让已有桌面业务继续处理。桌面导入项目包需要新增接口，当前尚未支持；手机仍可独立工作。

产品验收应关注：用户能否从书签迅速回到正确原音；识别积压时仍能准确标记；导出的音频、文字和时间轴是否对应；失败后是否能取回已保存内容。上述书签和片段导出属于基础首版之外的建议增量，需另行拆分工作量。

## Android 必须新增的部分

| 模块 | 首版职责 |
| --- | --- |
| 原生音频采集 | Android 10 / API 29 起的 AudioPlaybackCapture 与 MediaProjection；权限与授权生命周期；前台服务及系统通知 |
| 录制与会话管理 | 应用私有目录中的分段音频、会话索引、时间轴、停止尾包、空间不足处理和中断恢复 |
| ASR 适配器 | whisper.cpp 本机模型调用；有界排队、取消、错误及停止后补全 |
| 手机界面 | 开始／停止、日语文本、录音状态、识别积压、历史记录和回放；保留现有黑夜模式设计思路 |
| 文件导出 | 通过 Android 系统文件选择和分享机制导出；避免依赖桌面绝对路径或申请全盘文件访问 |
| 模型与资源管理 | 显式下载、完整性校验、加载状态、磁盘／运行内存提示、卸载和下载失败恢复 |

现有 Python 服务、桌面虚拟环境、MLX/Metal 不能直接打包成安卓推理应用。可以复用分段、队列、持久化和字幕导出的业务设计；Android 本机实现仍需要新的原生模块和推理适配。仅把网页包进 WebView，不会自动获得其他 App 的音频。

### 内录边界

- 需要用户授予音频录制权限和系统采集授权；目标 App 的音频捕获策略也必须允许。
- 不能承诺任意直播 App、受保护内容或通话音频都能采集。首版应先指定实际使用的直播 App，并验证其版本与设备组合。
- 持续无声应提示检查播放状态与采集来源，不能直接判定为 App 禁止内录，也不能自动切换麦克风。
- MediaProjection 授权结束、系统回收或音频设备变化后，必须准确显示采集状态，保存已收到的内容。需要重新授权时，不能后台自行恢复授权。
- Android 14 及更高版本需要按目标 SDK 处理 MediaProjection 前台服务和授权生命周期。
- 首版可用分屏或 App 内文本查看。若要求在直播 App 上方显示字幕，还需新增浮窗界面与授权，不包含在本次估算中。

## 手机本机方案的模型建议

推荐评估 Kotlin + Android NDK/JNI + whisper.cpp。模型使用支持日语的多语言版本，不能使用仅英语的 `.en` 模型；已有 MLX 权重及 Tiny 的 CTranslate2 权重都不能直接假定可用于该运行时。

| 模型候选 | 定位 | 开放条件 |
| --- | --- | --- |
| 多语言 Base | 首版优先测试的质量／速度折中 | 在目标手机和实际日语直播中验证持续速度、错字率与温度后再确定是否默认 |
| 多语言 Tiny | 资源较紧张时的候选 | 明确日语质量可能下降；由用户选择，不在 Base 失败后静默切换 |
| 多语言 Small | 后续高性能手机选项 | 先验证运行内存、持续负载和热降频；不承诺所有安卓手机实时运行 |

首轮以可用的 CPU 路径验证功能，再按实际设备评估成熟的 GPU/NPU 后端。不能因为手机有 NPU，就认为 Whisper 会自动获得加速。

只做识别后，无需在手机加载 Qwen，也没有 ASR 与翻译模型争抢内存的问题。但仍需测量系统可分配内存、模型峰值、运行一小时后的温度和识别积压。模型下载大小与运行内存分开显示，不能照搬 Mac 的统一内存估计。

仅用户点击下载后获取对应移动模型，下载来源和摘要固定、可校验。更换权重格式时重新核验来源；本次评估没有下载模型或确定仓库。

## 现有项目的复用边界

- `static/app.js:959–1002` 使用桌面 Edge 标签页共享和 AudioWorklet，Android 用原生采音替换。
- `yakiniku/model_runtime.py:119` 起依赖 MLX/Metal；Tiny 分支依赖 faster-whisper/CTranslate2。Android 另建 whisper.cpp 适配器和模型清单。
- `yakiniku/live_pipeline.py` 的有界队列、先保存音频再识别、失败片段补全等设计可复用，首版不接入其中的翻译队列。
- `yakiniku/storage.py` 中的音频分卷、原子保存、日语 SRT 导出及时间轴规则可作为 Android 持久化设计参考；文件操作由 Android 原生实现。
- 网页的布局、黑夜模式和按钮状态设计可参考；本机 Android 方案无需开放 FastAPI 服务的局域网访问，也无需新增远端音频传输。

## 验收重点

1. 指定目标手机、Android 版本和直播 App，先验证是否能持续采到内录音频。
2. 用实际日语直播比较 Tiny／Base；测量延迟、质量、积压、峰值内存和长时间温度，而非只测几秒演示。
3. 连续录制至少一小时；识别失败或变慢时，音频仍保持连续，页面明确显示缺口与待识别片段。
4. 通过实际采样数计算时间轴，处理分段去重；音频、TXT 与 SRT 内容对应。
5. 测试切到直播 App、锁屏、系统结束采集、蓝牙切换、来电和后台回收。采集实际中断后不能继续显示「正在录制」。
6. 强杀后重开可以发现未完成会话，恢复到最后已落盘位置；不承诺恢复尚未持久化的数据。
7. 测试剩余存储不足、模型缺失、加载失败以及导出失败。空间不足时安全停止，保留现有文件并提示原因。
8. 完成模型下载后关闭网络，仍可识别、保存、回放和导出。下载中断可以重试；模型未就绪时明确提示，不能静默改用其他模型或云端接口。

## 开发规模估计

这是新增 Android 客户端，按模块估算比统计修改几个现有文件更合适。

先用约 2–3 人日完成内录与模型持续速度验证；验证通过后，包含录制、识别、历史与导出的可用首版，累计约 10–15 人日。

这是限定一款目标手机和一个可采音直播 App 的原型／首版估算。不同厂商广泛适配、上架、签名发布、自动更新和悬浮字幕另计。模型速度或采音验证不通过时，需要先调整方案再重新估算；本次没有 Android 真机性能、内存或兼容性结论。
